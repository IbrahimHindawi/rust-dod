# 2.6 Adding and removing components

`ecs/src/2.components/2.6.add_remove/add_remove.rs`

A drone catches fire: it gains a `Burning` component. The fire goes out: it
loses it. Changing *what* an entity is, while the game runs, is the thing
your C kayan couldn't do, because its archetypes were structs fixed at compile
time. In an archetype ECS a table holds exactly one combination, so a drone
that gains a component no longer belongs in its table. **It moves:**

1. find the table for its signature plus (or minus) the component;
2. add a row there, and copy every component the two tables share;
3. swap-remove its old row, fixing whoever moves into the hole;
4. point its slot at the new table and row.

Its handle doesn't change. Everything else about it is where it was, one
table over.

## Step 1: the move

```rust
    fn move_to(&mut self, e: Entity, to: u32) {
        let Slot { table: from, row, .. } = self.slots[e.index as usize];
        if from == to {
            return;
        }
        let [old, new] = self.tables.get_disjoint_mut([from as usize, to as usize]).expect("two different tables");
        let new_row = new.add_row(e);
        for (o, n) in old.columns.iter().zip(new.columns.iter_mut()) {
            if let (Some(o), Some(n)) = (o, n) {
                n.row_mut(new_row).copy_from_slice(o.row(row as usize));
            }
        }
        old.remove_row(row as usize, &mut self.slots);
        self.slots[e.index as usize] = Slot { generation: e.generation, table: to, row: new_row as u32 };
    }
```

Every piece is something you've already built: `add_row` (2.3), a byte copy
per shared column (2.2), `remove_row` with its slot fix (1.4). Components only
the new table has start zeroed (`add_row` zeroes them). Components only the
old table has disappear with the old row.

The column loop zips the two tables' 64 column slots, id by id, and
`if let (Some(o), Some(n))` matches only the ids **both** tables have. That's
the "components the two tables share" from the list above, as a pattern.

A move costs one row copy in and one row copy out. That's cheap, but not
free, and it's why components that flip on and off every frame are sometimes
better as a field (an `on_fire: f32` inside `Health`) than as a component.

## Step 2: two tables at once

The move reads one table and writes another, so it needs both at the same
time, mutably. The obvious way doesn't compile:

```rust ignore
        let old = &mut self.tables[from as usize];
        let new = &mut self.tables[to as usize];
```

```
error[E0499]: cannot borrow `self.tables` as mutable more than once at a time
    |
534 |         let old = &mut self.tables[from as usize];
    |                        ----------- first mutable borrow occurs here
535 |         let new = &mut self.tables[to as usize];
    |                        ^^^^^^^^^^^ second mutable borrow occurs here
```

The compiler doesn't know `from` and `to` are different numbers. If they were
the same, `old` and `new` would be two `&mut` to one table, and that's the one
thing `&mut` promises never happens. So it refuses two `&mut` borrows of one
Vec, whatever the indices.

`get_disjoint_mut` is the standard answer. It takes the indices, **checks at
run time** that they're different (and in range), and hands back both:

```rust
        let [old, new] = self.tables.get_disjoint_mut([from as usize, to as usize]).expect("two different tables");
```

It returns a `Result`, and `expect` stops the program if the check fails. It
can't fail here, because `move_to` returned early when `from == to`. One
compare at run time, where the compiler couldn't prove it. You'll see this
trade again: when the borrow checker can't see that something is fine, Rust
usually has a checked way to say so, rather than an unsafe one.

`old.remove_row(row, &mut self.slots)` still works with `old` borrowed: `old`
borrows `self.tables`, and the slots are another field.

## Step 3: add and remove, typed

```rust
    fn add<T: Component>(&mut self, e: Entity, value: T) -> Result<(), Error> {
        if !self.alive(e) {
            return Err(Error::Dead);
        }
        if !self.has::<T>(e) {
            let from = self.slots[e.index as usize].table;
            let to = self.table_with(from, T::ID);
            self.move_to(e, to);
        }
        self.set(e, value)
    }
```

If the entity already has a `T`, adding is just setting. Otherwise it moves
to the table *with* `T`, then sets it. `remove::<T>` is the mirror image:
`Err(Missing)` if it has no `T`, otherwise a move to the table *without* `T`.

## Step 4: the archetype graph

Which table is "the table with `T`"? Its signature is the old one plus `T`'s
bit, so it could be looked up in `by_signature` every time. But a game
toggling components does that constantly, always between the same few
tables. So **each table remembers its neighbours**:

```rust
struct Table {
    signature: u64,
    capacity: usize,
    entities: Vec<Entity>,
    columns: [Option<Column>; 64],
    add_edges: [Option<u32>; 64],
    remove_edges: [Option<u32>; 64],
}
```

`add_edges[id]` is where this table's entities go when they gain component
`id`. `remove_edges[id]` is where they go when they lose it. `None` means
"not known yet". rin-dod stored *index + 1* so a zeroed table meant "not
known"; `Option<u32>` says it directly.

```rust
    fn table_with(&mut self, from: u32, id: u32) -> u32 {
        if let Some(to) = self.tables[from as usize].add_edges[id as usize] {
            self.edge_hits += 1;
            return to;
        }
        self.lookups += 1;
        let to = self.table_for(self.tables[from as usize].signature | bit(id));
        self.tables[from as usize].add_edges[id as usize] = Some(to);
        self.tables[to as usize].remove_edges[id as usize] = Some(from);
        to
    }
```

The first move from `{Position Velocity Health}` with `Burning` looks the
table up (and makes it). It then writes the answer on **both** tables: an add
edge one way and a remove edge back. After that, catching fire and putting it
out both follow edges. The tables and their edges form a graph, the
**archetype graph**, and flecs is built around it.

`table_for` can push a table and move them all, so each line after it indexes
`self.tables` afresh rather than keeping a reference from before. In rin that
was a comment saying so. Here it's the only way that compiles (2.4).

## Run it

```
4 drones:
    table 0 {Position Velocity Health}: 0:1 1:1 2:1 3:1
frame 1
    0:1 catches fire: ok
    2:1 catches fire: ok
    table 0 {Position Velocity Health}: 3:1 1:1
    table 1 {Position Velocity Health Burning}: 0:1 2:1
frame 2
    0:1 is put out: ok
    1:1 catches fire: ok
    2:1 catches fire: ok
...
frame 3
    1:1 is put out: ok
    2:1 is put out: ok
    3:1 is put out: missing
    3:1 catches fire: ok
...
2:1 moved tables twice and kept its data: at (30.00, 0.00), health 100
moves that looked up a table by signature: 1; that followed an edge: 6
verify: 0 problems
```

Watch row order shuffle as entities move: `3:1` jumps to row 0 of table 0
when `0:1` leaves. Order is never promised, and swap-remove is why. And one
lookup for seven moves: that's the graph working.

## Rust notes

| rin | Rust |
|---|---|
| `from: *kayan_table = ...; to: *kayan_table = ...;` | `get_disjoint_mut([from, to])`: two `&mut` at once, checked different at run time |
| `if (has(from, id) && has(to, id)) { memcpy(...) }` | `zip` the column slots, `if let (Some(o), Some(n))`, then `copy_from_slice` |
| `add_edges: [64]u32`, stored as index + 1 | `[Option<u32>; 64]`: `None` is "not known yet" |
| `kayan_remove<burning>(w, e)` | `w.remove::<Burning>(e)`: no value to pass, so the type is named |
| `kayan_add<burning>(w, e, { ... })` | `w.add(e, Burning { ... })`: the type comes from the value |

`copy_from_slice` panics if the two slices have different lengths. They
can't here (same component, same size), but if a bug ever made them differ,
the copy would stop the program instead of writing past a row.
