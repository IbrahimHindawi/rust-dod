# 1.2 Despawning, and reusing numbers

`ecs/src/1.entities/1.2.despawn/despawn.rs`

**In the dojo:** [1. free list and generations](../../dojo/1.free_list/README.md), on its own, to watch and to practise.

Games destroy things constantly: a bullet hits, a drone dies, an effect
fades. 1.1 could only add. This chapter adds `despawn`, and with it the first
real problem in ECS design: what happens to an entity's number when the entity
is gone?

## Step 1: a free list

If despawned numbers were never reused, a game firing one bullet a frame would
use up 8 numbers in 8 frames and 4 billion in a couple of years of play. More
to the point, every array would keep growing. So despawned numbers go on a
**free list**, and spawning takes from it first:

```rust
#[derive(Default)]
struct World {
    count: u32,
    alive: [bool; 8],
    free: [u32; 8],
    free_count: u32,
```

`count` is now how many numbers have *ever* been handed out, not how many
entities exist; the numbers on the free list are the gaps. `alive` says which
numbers are in use.

## Step 2: spawning reuses

```rust
    fn spawn(&mut self) -> Entity {
        let index = if self.free_count > 0 {
            self.free_count -= 1;
            self.free[self.free_count as usize]
        } else {
            assert!(self.count < 8, "the world is full");
            self.count += 1;
            self.count - 1
        };
        self.alive[index as usize] = true;
        Entity { index }
    }
```

The free list is a stack: the last number freed is the first reused.

## Step 3: despawning

```rust
    fn despawn(&mut self, e: Entity) {
        let i = e.index as usize;
        self.alive[i] = false;
        self.has_position[i] = false;
        self.has_velocity[i] = false;
        self.has_health[i] = false;
        self.free[self.free_count as usize] = e.index;
        self.free_count += 1;
    }
```

Despawning lowers every flag, so the entity's old components can't leak into
whatever reuses the number. The values stay in the arrays, but with the flags
down nobody reads them. Systems need no change: a despawned entity has no
flags, so movement skips it without knowing anything about despawning.

## Step 4: the bug

Now the problem. Things in a game refer to other things: a turret aims at a
drone, a missile chases a target, a health bar follows a unit. With entities
as numbers, a reference is a number:

```rust
    let target = drone_a;
```

The program then destroys the drone, and the turret fires. The bullet is a
new entity, and it takes the first free number, the drone's:

```
the turret targets entity 1, a drone
...
entity 1 is destroyed and despawned
    entity 1  (free)
the turret fires: the bullet is entity 1
...
the turret aims at entity 1, at (2.00, 2.00), moving (4.00, 4.00)
    that is the turret's own bullet, not the drone: the number was reused
```

Nothing told the turret its target died, and nothing could: references can be
anywhere, in any number of places. The number in `target` is still a valid
number, it just names a different entity now. No crash, no error, just a
turret shooting at its own bullet. In a real game this is the bug where a
homing missile turns around mid-flight, or a health bar jumps to another unit.

**Rust doesn't catch this.** The borrow checker tracks *references*: a `&Vec2`
pointing at the drone's position could not outlive the drone. But `target` is
a number, copied out of an `Entity`, and the borrow checker has nothing to say
about numbers. A stale number is a logic bug, and logic bugs compile. Keep
that in mind: this course will meet it again, and Rust's guarantees stop at the
same place each time.

## Run it

```
the turret targets entity 1, a drone
    entity 0  position ( 0.00,  0.00)  velocity -                health 500
    entity 1  position (10.00,  0.00)  velocity (-1.00,  0.50)  health 100
    entity 2  position ( 0.00, 10.00)  velocity ( 0.50, -1.00)  health 100
entity 1 is destroyed and despawned
    entity 0  position ( 0.00,  0.00)  velocity -                health 500
    entity 1  (free)
    entity 2  position ( 0.00, 10.00)  velocity ( 0.50, -1.00)  health 100
the turret fires: the bullet is entity 1
...
```

## Why not just...

- **...never reuse numbers?** The arrays would grow forever, and every system
  would walk an ever-longer list of dead numbers.
- **...find and clear every reference on despawn?** You'd need to know where
  every reference lives. That's exactly what an ECS is trying to avoid: things
  refer to each other loosely, by number.
- **...check `alive[target.index]`?** It says `true`: the number *is* alive.
  It's alive as a different entity, and nothing can tell the two apart.

The next chapter tells them apart with one extra number per entity.

## Rust notes

| rin | Rust |
|---|---|
| `e: kayan_entity = {}; if (...) { e.index = ...; } else { ... }` | `let index = if ... { ... } else { ... };`: `if` is an expression, and each branch's last line is its value |
| `_ = movement_system(...)` | `movement_system(&mut w, 0.5);`: an ordinary return value may be dropped silently |
| an out-of-range index, unchecked in a Release build | every array index is checked, in Release too; past the end, the program stops |
