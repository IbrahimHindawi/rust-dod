# 2.5 Typed access

`ecs/src/2.components/2.5.typed_access/typed_access.rs`

**In the dojo:** [4. a type-erased column](../../dojo/4.column/README.md), [8. index, not pointer](../../dojo/8.index/README.md), each on its own, to watch and to practise.

The world stores any component in any combination, as bytes. Game code
should never see the bytes. This chapter adds the **typed layer** on top:

```
w.get::<Position>(e)        -> Option<&Position>
w.get_mut::<Health>(e)      -> Option<&mut Health>
w.has::<Velocity>(e)        -> bool
w.set(e, value)             -> Ok, or Err(Dead), or Err(Missing)
```

Each is a few lines that turn the type into an id, find the entity's table
and row through its slot, and hand the row back as a `T`. The byte-level core
underneath doesn't change at all. This is the split from 2.2: byte work
below, typed generic functions on top, each written once.

## Step 1: get

```rust
    fn get<T: Component>(&self, e: Entity) -> Option<&T> {
        if !self.alive(e) {
            return None;
        }
        let t = self.table_of(e);
        if !t.has(T::ID) {
            return None;
        }
        Some(&t.slice::<T>()[self.row(e)])
    }
```

Handle, slot, table, row, typed view. It's the same path as 1.4's
`get_position`, for any component. Two ways to get `None`: the handle is
dead, or the entity has no `T`. The caller checks once and then has a real
reference.

`get_mut` is the same with `&mut`, so the caller can change the component in
place:

```rust
    w.get_mut::<Health>(a).expect("a is a drone").points -= 25.0;
```

## Step 2: has and set

```rust
    fn has<T: Component>(&self, e: Entity) -> bool {
        self.signature(e) & mask_of::<T>() != 0
    }
```

`has` doesn't touch the row at all. An entity's components are its table's
signature, one AND away.

```rust
    fn set<T: Component>(&mut self, e: Entity, value: T) -> Result<(), Error> {
        if !self.alive(e) {
            return Err(Error::Dead);
        }
        *self.get_mut::<T>(e).ok_or(Error::Missing)? = value;
        Ok(())
    }
```

`set` writes a component the entity already has. Giving it a component it
*doesn't* have changes which table it belongs in, and that's 2.6. So the
error gains a second value:

```rust
enum Error {
    Dead,
    Missing,
}
```

The middle line of `set` packs three steps. `ok_or(Error::Missing)` turns the
`Option<&mut T>` into a `Result`: the reference, or `Err(Missing)`. The `?`
returns that error from `set` right away, or unwraps the reference. Then
`*... = value` writes through it. `?` is how Rust functions pass an error up
without an `if` for every call.

`set` needs no type argument. `w.set(e, Health { ... })` names `Health` by
the value, and the compiler works out `T` from it.

## Step 3: building things

With `set`, game code builds entities with small functions. Engines call
these prefabs or archetype constructors:

```rust
fn spawn_drone(w: &mut World, x: f32, y: f32) -> Entity {
    let e = w.spawn(mask_of::<Position>() | mask_of::<Velocity>() | mask_of::<Health>());
    w.set(e, Position { at: Vec2 { x, y } }).expect("just spawned");
    w.set(e, Velocity { per_second: Vec2 { x: -1.0, y: 0.0 } }).expect("just spawned");
    w.set(e, Health { points: 100.0, max: 100.0 }).expect("just spawned");
    e
}
```

`expect("just spawned")` says why each `set` can't fail: the entity was just
spawned with exactly these components. If that's ever wrong, the program
stops on the line that was wrong about it.

Reading two components at once is a `match` on both `Option`s:

```rust
    match (w.get::<Position>(e), w.get::<Health>(e)) {
        (Some(p), Some(h)) => println!("    {e} at ({:5.2}, {:5.2}), health {:.0}", p.at.x, p.at.y, h.points),
        _ => println!("    {e} is not a live drone"),
    }
```

Both are shared borrows of the world, so they can be held at the same time.

## Step 4: keep handles, borrow references

The reference `get_mut` returns points into a column. 2.2 showed what columns
do when their table fills up: they move. So a reference is good **until the
next structural change**: a spawn, a despawn, or (from 2.6) an add or remove.

In rin-dod, this is where the program kept a pointer to a drone's health,
spawned 8 drones so the table grew, and wrote through the pointer. The write
landed in the column's old block, and was lost without a sound. Here is the
same thing in Rust:

```rust ignore
    let kept = w.get_mut::<Health>(a).expect("a is a drone");
    let mut last = a;
    for i in 0..8 {
        last = spawn_drone(&mut w, 40.0 + i as f32, 0.0);
    }
    kept.points = 1.0;
```

```
error[E0499]: cannot borrow `w` as mutable more than once at a time
    |
606 |     let kept = w.get_mut::<Health>(a).expect("a is a drone");
    |                - first mutable borrow occurs here
...
609 |         last = spawn_drone(&mut w, 40.0 + i as f32, 0.0);
    |                            ^^^^^^ second mutable borrow occurs here
610 |     }
611 |     kept.points = 1.0;
    |     ----------------- first borrow later used here
```

`kept` borrows the world, and `spawn_drone` needs the world, so they can't
overlap. The bug from rin-dod doesn't build. Nothing about columns moving is
in the error; the compiler only knows that `kept` must not outlive anything
that could change the world. That's enough.

So the program shows the bug that *does* build. Instead of a reference, it
keeps a **row number**:

```rust
    let kept_row = w.row(a);
    w.despawn(a).expect("alive");
    w.table_of_mut(last).slice_mut::<Health>()[kept_row].points = 1.0;
```

```
kept 0:1's row number, 0, despawned 0:1, then wrote health 1 into row 0:
    9:1 at (47.00,  0.00), health 1
    the last drone moved into the hole, so the write hit 9:1; the handle 0:1 says dead
```

The despawn swap-removed `0:1`'s row, the last drone moved into it, and the
write hit that drone instead. A row number is a number, like 1.2's entity
number, and the borrow checker has nothing to say about numbers. Hence the
rule every ECS has in some form:

**Keep handles. Borrow references: get, use, forget.**

In Rust, the "forget" half is enforced for references and not for row
numbers. A handle is the one thing that's safe to keep, because the world
checks it every time.

## Run it

```
two drones and a bullet, built with set:
    0:1 at (20.00,  5.00), health 100
    1:1 at (30.00, -5.00), health 100
drone 0:1 is hit through get_mut::<Health>:
    0:1 at (20.00,  5.00), health 75
the bullet has a velocity: yes; a health: no
get::<Health> on the bullet is None: yes
set(Health) on the bullet: missing
despawned 1:1; set(Health) on it now: dead
    1:1 is not a live drone
...
verify: 0 problems
```

## Rust notes

| rin | Rust |
|---|---|
| `kayan_get<T>(w, e) -> *T`, or `null` | `w.get::<T>(e) -> Option<&T>`, and `get_mut` for `Option<&mut T>` |
| `kayan_status.missing` | `Err(Error::Missing)` |
| `p: *T = ...; if (p == null) { return missing; } p* = value;` | `*self.get_mut::<T>(e).ok_or(Error::Missing)? = value;` |
| `kayan_set<health>(w, e, ...)` | `w.set(e, Health { ... })`: `T` comes from the value |
| `_ = kayan_set<...>(...)` | `.expect("just spawned")`: the reason it can't fail, checked |
| a pointer kept across a spawn: compiles, writes are lost | a reference kept across a spawn: E0499, doesn't compile |
| a row number kept across a despawn | the same: compiles, and writes the wrong entity |
