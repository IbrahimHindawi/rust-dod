# 2.1 Components and signatures

`ecs/src/2.components/2.1.components/components.rs`

**In the dojo:** [6. bitsets](../../dojo/6.bitset/README.md), on its own, to watch and to practise.

Part 1 hard-coded its components: a `positions` Vec, a `velocities` Vec, a
flag for each. Adding a component meant editing the world, `spawn`, `despawn`
and every printer. Part 2 builds a world that works for components it has never
heard of. This chapter lays the ground with four ideas:

1. A component is a plain struct.
2. Each component type has an **id**, a small number fixed at compile time.
3. The world keeps a **registry**: per id, the component's size, alignment and
   name, which is all it needs to store bytes it doesn't understand.
4. A set of components is a **signature**: one bit per id in a `u64`.

There are no entities in this chapter. 2.3 puts the two halves together.

## Step 1: components are plain structs

```rust
component!(Position { at: Vec2 });
component!(Velocity { per_second: Vec2 });
component!(Health { points: f32, max: f32 });
component!(Damage { amount: f32 });
component!(Lifetime { seconds: f32 });
component!(Burning { per_second: f32 });
component!(Turret { cooldown: f32, timer: f32 });
```

Each line declares a struct with those fields, plus what the world needs to
know about it (Step 4 opens the macro up). No methods, no references to other
entities, no idea that a world exists. That's deliberate. Behaviour belongs to
systems, and data that knows nothing can be copied, moved and stored as raw
bytes, which the world is about to do.

Why `Position { at: Vec2 }` rather than using `Vec2` directly? Because a
component's *type* is how the world tells components apart. Position and
velocity are both two floats, but they're different things, and making them
different types is what lets you ask for one and not the other.

## Step 2: an id per component type

```rust
#[derive(Clone, Copy)]
enum ComponentId {
    Position,
    Velocity,
    Health,
    Damage,
    Lifetime,
    Burning,
    Turret,
}
```

The enum gives each component a number: its position in the list. Every
component implements a trait that carries its id, and its reflect record:

```rust
trait Component: Copy + 'static {
    const ID: u32;
    const INFO: &'static Info;
}
```

`Position::ID` is a constant, `0`, known at compile time. Nothing is looked up
at run time; in generated code, the id is just a number.

`Copy + 'static` says what a component may be: something you can copy byte for
byte, holding no borrowed references. That rules out a `String` or a `Vec`
inside a component (they own memory elsewhere, so copying their bytes would
copy a pointer, not the data). Components are their bytes and nothing else.

## Step 3: the world speaks ids, never types

The world can't be generic over component types. Which combinations exist is
only known while the game runs. So the world works in ids and bits, and a small
**typed layer** translates:

```rust
fn bit(id: u32) -> u64 {
    1 << id
}

// The typed layer: from a type to the bit the world works in.
fn mask_of<T: Component>() -> u64 {
    bit(T::ID)
}
```

Game code says `mask_of::<Velocity>()`, and the world only ever sees `2`, a
bit.

## Step 4: the reflect record, written by the compiler

To store a component as bytes, the world needs three facts about it: how many
bytes, what alignment, and a name for printing. The compiler knows all three,
and the `component!` macro asks it to write them down:

```rust
macro_rules! component {
    ($name:ident { $($field:ident: $ty:ty),* $(,)? }) => {
        #[derive(Clone, Copy, Default, Debug)]
        struct $name {
            $($field: $ty),*
        }

        impl Component for $name {
            const ID: u32 = ComponentId::$name as u32;
            const INFO: &'static Info = &Info { name: stringify!($name), layout: Layout::new::<$name>() };
        }
    };
}
```

`macro_rules!` matches the text you write (`Position { at: Vec2 }`) and expands
it into code. Here it writes the struct, then the trait impl:

- the id is the enum variant with the *same name* as the struct;
- `stringify!($name)` turns the name into the string `"Position"`;
- `Layout::new::<Position>()` is the compiler's own size and alignment.

The record is a constant, built at compile time and stored in the program, the
same thing rin's `position<>` is.

```rust
struct Info {
    name: &'static str,
    layout: Layout,
}
```

## Step 5: the registry

The registry is an array of records, indexed by id:

```rust
struct World {
    infos: [Option<&'static Info>; 64],
    component_count: u32,
}
```

```rust
    fn register<T: Component>(&mut self) {
        assert!(T::ID < 64, "component id {} is past the 64 a signature can hold", T::ID);
        self.infos[T::ID as usize] = Some(T::INFO);
        self.component_count = self.component_count.max(T::ID + 1);
    }
```

Registering needs nothing but the type: `w.register::<Position>()`. Inside a
generic function, `T::ID` and `T::INFO` work for whatever `T` is.

## Step 6: signatures

A set of components is a `u64` with a bit set per component in the set. What
a thing *is* is a signature:

```rust
    let drone = mask_of::<Position>() | mask_of::<Velocity>() | mask_of::<Health>();
```

Every question you'd ask about sets is a bit operation:

```rust
fn contains(signature: u64, wanted: u64) -> bool {
    (signature & wanted) == wanted
}
```

"Does this drone have what movement wants?" is `contains(drone, moves)`, one
AND and one compare. Adding a component is `|`, and removing one is `& !`:

```rust
    let put_out = burning_drone & !mask_of::<Burning>();
```

64 bits means at most 64 component types per world, which is plenty for
learning and for most games. Larger ECSs use wider bitsets or sorted id
lists; the idea is the same.

```
    drone yes, bullet yes, turret no, burning drone yes

```

Read the bits as a table: each column is a component, each row a kind of
thing. That table is the next three chapters. Each distinct row will become
a table of its own.

## Rust notes

| rin | Rust |
|---|---|
| `component_of: proc<position>() -> component = { ... }`, once per type | `impl Component for Position { const ID: u32 = ...; }`: a trait with an associated constant |
| `position<>`, the compiler's reflect record | `Layout::new::<Position>()` and `stringify!`, written into a constant by a macro |
| `kayan_id_of<T>()` | `T::ID`, inside any function generic over `T: Component` |
| `kayan_mask_of<velocity>()` | `mask_of::<Velocity>()`: the `::<>` ("turbofish") names the type when nothing else does |
| `~mask` | `!mask`: on integers, `!` flips every bit |
| a generic `kayan_register<T>` that needed a compiler fix | `fn register<T: Component>(&mut self)`, from day one |

In Rust, as in rin, `&` binds tighter than `==`, so `signature & wanted ==
wanted` would also mean what it says. The program keeps the parentheses for
anyone coming from C, where it doesn't.
