# 3.4 A game

`ecs/src/3.systems/3.4.game/game.rs`

Everything together. Three lanes, a turret at the left end of each, and
drones coming from the right in waves:

- a turret fires down its lane while there's a drone in it;
- a bullet that reaches a drone damages it;
- a drone below half health catches fire;
- a drone with no health left is destroyed;
- a drone that gets to the left end has reached the base.

The top of the file is kayan, exactly as 3.3 left it. The game is the bottom:
kernels, systems, a schedule and a level script. Every rule of the game is a
system over a query. Every structural change a system makes is a command.

## The pieces

The components are the same seven from 2.1. A drone is a signature:

```rust
fn drone_signature() -> u64 {
    mask_of::<Position>() | mask_of::<Velocity>() | mask_of::<Health>()
}
```

A burning drone is that plus `Burning`, which puts it in another table. There
is no `Drone` type anywhere in the program. A drone is whatever lives in a
table with these columns.

What the systems share (the drones query, the clock, the score) is one
struct, the schedule's context (3.3):

```rust
struct Game {
    drones: Query,
    time: f32,
    fired: u32,
    hits: u32,
    fires: u32,
    kills: u32,
    breaches: u32,
    came: u32,
}
```

Every system in the schedule gets `&mut Game`. The ones that use it name it
(`g: &mut Game`); the rest are generic and ignore it.

## The schedule

```rust
    let mut systems = [
        System::new("turret", shooting, 0, turret_system),
        System::new("age", mask_of::<Lifetime>(), 0, age_system),
        System::new("expire", mask_of::<Lifetime>(), 0, expire_system),
        System::new("move", movers, 0, move_system),
        System::new("hit", bullets, 0, hit_system),
        System::new("ignite", mask_of::<Health>(), mask_of::<Burning>(), ignite_system),
        System::new("burn", mask_of::<Health>() | mask_of::<Burning>(), 0, burn_system),
        System::new("die", mask_of::<Health>(), 0, die_system),
        System::new("breach", mask_of::<Position>() | mask_of::<Health>(), 0, breach_system),
    ];
```

Read it as the frame, top to bottom. Each line's position is a data-flow
decision (3.2):

- `move` before `hit`: bullets hit where they are, not where they were.
- `hit` before `ignite`, `burn` and `die`: a drone takes damage, catches fire
  and is destroyed in the same frame its health drops.
- `die` before `breach`: only a drone that survived the frame can reach the
  base. `breach` also checks `points > 0` itself, because both run in the
  same frame and `die`'s despawn hasn't been applied yet.
- `ignite` has `none {Burning}`: a drone catches fire once. The add is a
  command, so next frame it's in the burning table and the query no longer
  matches it.

The array's type is `[System<Game>; 9]`, and nobody wrote that down. The
compiler works it out from `turret_system`, which takes `&mut Game`, and then
picks `C = Game` for every generic system in the list.

## The rules

Each one is a few lines. The ones that only change values call kernels:

```rust
fn burn_system<C>(it: &mut Iter, _ctx: &mut C) {
    let (hs, fires) = it.tables[it.table].pair_mut::<Health, Burning>();
    burn(hs, fires, it.dt);
}
```

The ones that change structure record commands:

```rust
        if h.points < 0.5 * h.max && h.points > 0.0 {
            it.commands.add(e, Burning { per_second: 10.0 });
            g.fires += 1;
        }
```

The turret is the most involved. It asks the drones query whether anything
is ahead of it in its lane, then spawns a bullet with a pending spawn (3.3).
It needs its own row and the drones' tables, which are all in `it.tables`, so
it takes them **one after another**: copy the row's values out, look at the
drones, then borrow the row again to write the timer.

```rust
        let p = it.tables[it.table].slice::<Position>()[row];
        let ready = it.tables[it.table].slice::<Turret>()[row].timer <= 0.0;
        if ready && drone_ahead(it.tables, &g.drones, p.at.x, p.at.y) {
```

`p` is a copy, not a reference (components are `Copy`), so nothing is
borrowed when `drone_ahead` reads all the tables. rin's version held a
pointer into the turret column across the call; Rust makes you say which
borrow comes first. Here it costs nothing, and the order is clearer.

`hit` is 3.3's hit system, with one extra thought about speed. A bullet
moves a unit a frame and a fast drone a quarter, so they close by at most
1.25 a frame. A hit window of ±0.75 is 1.5 wide, so no bullet can pass
through a drone between two frames:

```rust
                if dx * dx < 0.5625 && dy * dy < 0.25 {
```

## The level

The waves aren't a system. They're the level script, and it runs **between**
frames, in the game loop, where spawning directly is safe:

```rust
    for frame in 0..frames {
        g.time = frame as f32 * dt;
        if frame % 32 == 0 && frame / 32 < 8 {
            send_wave(&mut w, &mut g, frame / 32);
        }
        progress(&mut w, &mut systems, &mut g, dt);
        problems += w.verify();
```

`verify` runs after every frame: 512 checks of Part 1's invariant over the
whole world.

## Drawing by table

The picture of the lanes walks a query of everything with a position. What
an entity is drawn as comes from its **table's signature**, decided once per
table, not per entity:

```rust
fn glyph_of(signature: u64) -> char {
    if signature & mask_of::<Turret>() != 0 {
        'T'
    } else if signature & mask_of::<Burning>() != 0 {
        '*'
    } else if signature & mask_of::<Health>() != 0 {
        'd'
    } else {
        '-'
    }
}
```

In an OOP engine this would be a virtual `draw()` per object, or in Rust a
`dyn Draw` trait object. Here it's a property of a table, and the inner loop
is a plain loop over positions.

## Exact on purpose

Every speed and time step is a power of two: `dt` is 1/16, drones move 2 or 4
units a second, bullets 16, fire burns 10 a second (0.625 a frame). So every
position, health and timer is exactly representable, and no rounding ever
happens. Rust also never fuses a multiply and an add into one instruction on
its own (C compilers may). That's why a Debug build and a Release build print
the same game, and why it matches rin-dod's line for line. Real games give
that up for nicer numbers. Rounding differences usually don't matter, but
they do the day you want a replay or a lockstep network game.

## What you built

```
Part 1  entities       handles, generations, slots, swap-remove, verify
Part 2  components     ids, columns, tables, archetypes, typed access,
                       moving between tables, the archetype graph, reflection
Part 3  systems        queries, kernels and schedules, commands, a game
```

That's a working archetype ECS, about 700 lines of kayan without comments,
with five one-line `unsafe` blocks, no dependencies, and a clean run under
Miri. It's the design flecs is built on (tables, the archetype graph, cached
queries, command buffers), and Bevy and Unity DOTS are close cousins, minus
their years of features.

## What Rust changed

Across the course, the borrow checker turned three of rin-dod's quiet bugs
into compile errors:

| chapter | the bug | in rin | in Rust |
|---|---|---|---|
| 2.4 | a table pointer kept across `table_for` | a row in a table that moved | E0499 |
| 2.5 | a component pointer kept across a spawn | a write lost in an old block | E0499 |
| 3.3 | despawning while iterating a table | a row skipped | E0502 |

And it caught none of the bugs about **numbers**: 1.2's reused entity
number, 2.5's stale row number, 3.3's loop over row numbers. Those are what
generations, handles and commands are for, in either language. The borrow
checker tracks who may touch memory; it doesn't know what a number means.

It also turned two conventions into types: a system can't change structure,
because `Iter` has no world (3.2), and a system's context is checked, not
cast (3.3). And it cost three things rin didn't have: `get_disjoint_mut`
where two tables or columns are needed at once, `std::mem::take` to apply
commands to the world that owns them, and a few borrows taken one after
another instead of held together (the turret, 2.3's writes).

## Next

Things worth adding, roughly in order of how much they teach:

- **Relationships**: `ChildOf(parent)` as a component, flecs' big idea.
- **Change detection**: a per-column version number, so a system can skip
  tables nothing wrote to.
- **Parallel systems**: systems that don't write what others read can run at
  the same time. In Rust, that's two `&mut` borrows that don't overlap, so
  `std::thread::scope` and `split_at_mut` (or `get_disjoint_mut`) are most of
  what's needed, and the compiler checks the split.
- **Removing empty tables**, and the queries' table lists with them.
- **Serialization**: the reflect records already describe every byte; write
  the tables out and read them back.
