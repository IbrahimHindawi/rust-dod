# 3.2 Systems

`ecs/src/3.systems/3.2.systems/systems.rs`

3.1's movement loop had the shape of every system: bring a query up to date,
then for each of its tables take the columns as slices and loop over the rows.
This chapter names that shape and splits it in two:

- **the kernel**: a plain loop over plain slices. It knows nothing about
  tables, entities or worlds. This is lessons 1 to 7: streaming, aliasing,
  vectorization.
- **the system**: a query, plus a small function kayan calls on each table
  the query matches. It takes the table's columns and calls the kernel.

A frame runs the systems in order, each over all of its tables. The order is
the **schedule**, and it's written down once, as data.

## Step 1: the kernels

```rust
fn integrate(ps: &mut [Position], vs: &[Velocity], dt: f32) {
    for (p, v) in ps.iter_mut().zip(vs) {
        p.at.x += v.per_second.x * dt;
        p.at.y += v.per_second.y * dt;
    }
}
```

That's the whole thing, and it's the code you'd want to write if there were
no ECS at all. Kernels are where you profile, read assembly and reach for
SIMD (the lessons). Everything else in this course exists to hand them the
right slices. `burn` and `age` look the same.

rin writes `ps: noalias []position` to promise the compiler that nothing else
reaches `ps`, so it can vectorize without checking for overlap. In Rust, every
`&mut` slice already makes that promise, and the borrow checker is what keeps
it true. There's nothing to write.

## Step 2: what a system gets

```rust
struct Iter<'a> {
    tables: &'a mut [Table],
    table: usize,
    dt: f32,
}

type SystemFn = fn(&mut Iter<'_>);
```

One struct instead of three parameters. It's the same idea as flecs'
`ecs_iter_t`: adding to it later (3.3 adds a field) changes no system's
signature.

`Iter<'a>` holds a borrow, so it carries a **lifetime**, `'a`: the struct
can't outlive the tables it borrows. You write `'a` on the struct and
`'_` ("some lifetime, whichever") where it's used, and the compiler does the
rest. This is the first struct in the course that holds a reference; the
rest own their data.

Note what's **not** in it: the world. rin's `kayan_iter` had a `world`
pointer, and through it a system could call `kayan_despawn` in the middle of
a frame. Here a system gets the tables, and spawn, despawn, add and remove are
methods of `World`, which it can't reach. A system can change values, never
structure, and that's a rule of the types now, not a convention. 3.3 is about
what to do when a system *needs* to change structure.

The system itself is the adapter:

```rust
fn move_system(it: &mut Iter) {
    let (ps, vs) = it.tables[it.table].pair_mut::<Position, Velocity>();
    integrate(ps, vs, it.dt);
}
```

Columns out, kernel in. No loop here: the kernel has it. `ps` and `vs` borrow
`it.tables`, and `it.dt` is another field, so reading it alongside is fine.

## Step 3: a system is data

```rust
struct System {
    name: &'static str,
    query: Query,
    run: SystemFn,
    calls: usize,
    rows: usize,
}
```

A name, a query, a function pointer. `calls` and `rows` count the work, for
the output. The schedule is an array of these:

```rust
    let mut systems = [
        System::new("burn", mask_of::<Health>() | mask_of::<Burning>(), 0, burn_system),
        System::new("age", mask_of::<Lifetime>(), 0, age_system),
        System::new("move", mask_of::<Position>() | mask_of::<Velocity>(), 0, move_system),
    ];
```

`move_system` without parentheses is the function itself, as a value of type
`SystemFn`. No allocation, no trait object: a plain pointer to code, as in
rin.

## Step 4: a frame

```rust
fn progress(w: &mut World, systems: &mut [System], dt: f32) {
    for s in systems.iter_mut() {
        s.query.update(&w.tables);
        for &ti in &s.query.tables {
            let rows = w.tables[ti as usize].count();
            if rows > 0 {
                s.calls += 1;
                s.rows += rows;
                (s.run)(&mut Iter { tables: &mut w.tables, table: ti as usize, dt });
            }
        }
    }
}
```

`progress` is flecs' name for the same thing. For each system in order, for
each of its tables, one call. `(s.run)(...)` calls the function in the `run`
field; the parentheses tell Rust it's a field, not a method named `run`. The
game loop becomes:

```rust
    for frame in 1..=8 {
        progress(&mut w, &mut systems, dt);
```

The systems live outside the world, in `main`'s own array, so `progress` can
borrow a system's query while lending the world's tables to the system. If the
schedule were a field of the world, the two borrows would overlap.

## Order is data flow

Systems run one after another, never interleaved, and each sees everything
the earlier ones wrote this frame. So the order is a statement about data: a
system that **reads** what another **writes** runs after it. Move before
collide means bullets hit where they are now, not where they were. Damage
before death means a drone dies in the frame its health hits zero, not the
next. 3.4's schedule has nine systems, and each position in it is one of
these decisions.

Bigger engines go further. Each system declares what it reads and writes,
and the scheduler uses that to run systems that don't conflict at the same
time, on other threads. Underneath, the order is still a list like this one.
In Rust, "doesn't conflict" is exactly the borrow checker's question: two
systems can run at once if neither needs `&mut` of what the other touches.

## Run it

```
the schedule, run in this order every frame:
burn: all {Health Burning}, none {}; tables: 1, entities: 1
    table 2 {Position Velocity Health Burning}: 2:1
age: all {Lifetime}, none {}; tables: 1, entities: 3
    table 3 {Position Velocity Damage Lifetime}: 4:1 5:1 6:1
move: all {Position Velocity}, none {}; tables: 3, entities: 6
    table 1 {Position Velocity Health}: 1:1 3:1
    table 2 {Position Velocity Health Burning}: 2:1
    table 3 {Position Velocity Damage Lifetime}: 4:1 5:1 6:1
...
after frame 8, 2.00 seconds:
    0:1 at ( 0.00,  0.00)
    1:1 at (18.00,  4.00)  health 100
    3:1 at (26.00, -4.00)  health 100
    2:1 at (22.00,  0.00)  health 84, burning
    4:1 at (17.00,  0.00)  lifetime -1.50
    5:1 at (17.00,  4.00)  lifetime -1.00
    6:1 at (17.00, -4.00)  lifetime -0.50

8 frames, one call per table per frame:
    burn called  8 times, over  8 rows
    age  called  8 times, over 24 rows
    move called 24 times, over 48 rows
3 bullets are out of time and still in the world
```

`move` made 24 calls in 8 frames, three tables a frame, and each call is one
tight loop. Call overhead is per table, never per entity.

And the last line is the cliffhanger. Each bullet's lifetime ran out, and
nothing removed it, because a system in this chapter changes values, never
structure. Despawning from inside a system looks like a one-line fix. It
isn't, and 3.3 shows why.

## Rust notes

| rin | Rust |
|---|---|
| `ps: noalias []position` | `ps: &mut [Position]`: every `&mut` is already "noalias" |
| `kayan_iter { world, table, dt }` | `Iter<'a> { tables, table, dt }`: no world, so no structural changes |
| `kayan_system_proc: alias = *proc(it: *kayan_iter) -> void` | `type SystemFn = fn(&mut Iter<'_>)` |
| `sys*.run(it&)` | `(s.run)(&mut Iter { ... })` |
| `systems: [3]kayan_system = {}; systems[0] = ...;` | `let mut systems = [System::new(...), ...]` |
| an unused parameter is an error (`-Wextra -Werror`) | the same under `-D warnings`; naming it `_it` says it's unused on purpose |
