# 3.3 Commands

`ecs/src/3.systems/3.3.commands/commands.rs`

3.2's systems change values, never structure, so bullets whose time ran out
stay in the world. The obvious fix is to despawn them from inside the loop
that walks their table. It's wrong, and seeing exactly why is most of this
chapter. Rust catches part of it, which makes the part it doesn't catch
easier to see.

## Step 1: the bug

The natural way to write it is a loop over the table's rows that despawns as
it goes:

```rust ignore
fn expire_now(w: &mut World, table: usize) {
    let t = &w.tables[table];
    for (&e, l) in t.entities.iter().zip(t.slice::<Lifetime>()) {
        if l.seconds <= 0.0 {
            w.despawn(e).expect("alive");
        }
    }
}
```

It doesn't compile:

```
error[E0502]: cannot borrow `*w` as mutable because it is also borrowed as immutable
     |
1061 |     let t = &w.tables[table];
     |              -------- immutable borrow occurs here
1062 |     for (&e, l) in t.entities.iter().zip(t.slice::<Lifetime>()) {
     |                    -------------------------------------------- immutable borrow later used here
1063 |         if l.seconds <= 0.0 {
1064 |             w.despawn(e).expect("alive");
     |             ^^^^^^^^^^^^ mutable borrow occurs here
```

The loop borrows the table, and `despawn` needs the whole world, table
included. The compiler doesn't know what `despawn` does to the table; it only
knows it *could* change it while the loop is reading it. In rin, this version
compiles and has the bug. So the program writes the version that compiles in
Rust too, a loop over row **numbers**:

```rust
fn expire_now(w: &mut World, table: usize) {
    let mut row = 0;
    while row < w.tables[table].count() {
        if w.tables[table].slice::<Lifetime>()[row].seconds <= 0.0 {
            let e = w.tables[table].entities[row];
            w.despawn(e).expect("alive");
        }
        row += 1;
    }
}
```

Each line borrows the table for a moment and lets go, so nothing is borrowed
when `despawn` runs. Four bullets, three of them out of time:

```
1. an expire loop that despawns as it goes
    lifetimes:  0:1 0.00  1:1 1.00  2:1 0.00  3:1 0.00
after one pass:
    lifetimes:  3:1 0.00  1:1 1.00
verify: 0 problems. The world is fine; the loop missed one.
```

Row by row:

```
row 0: 0:1 is out of time. Despawn: the last row, 3:1, moves into row 0.
row 1: 1:1 has time left.
row 2: 2:1 is out of time. Despawn: it's the last row, so nothing moves.
row 3: the table has 2 rows now. Stop.
```

`3:1` moved into row 0, which the loop had already passed, so it was never
looked at. The world is perfectly consistent (`verify` agrees). The *loop* is
what's wrong: a despawn swap-removes from the table the loop is walking. A
row number is a number, and 2.5 already showed what the borrow checker says
about those: nothing.

Walking backwards fixes this case (lesson 2 does it), because the row that
moves in has already been looked at. But it doesn't fix the general problem:

- **Adding or removing** a component moves the entity to *another* table. If
  the query matches that table too and visits it later, the entity is
  processed twice.
- If that table is **new**, making it can grow `w.tables` and move every
  table. In rin, the table pointer the loop holds then points at the old
  copy, and every write after that is lost. In Rust, a reference couldn't
  survive that (2.4), but a table *index* would, and so would the confusion.
- One system's despawn can land in a table **another** system is halfway
  through, if a system despawns entities it found through a second query.

## Step 2: record now, apply later

So a system doesn't change structure. It records a **command** saying what
should change, and the world applies every command after the frame's last
system:

```
during the frame   values change; tables, rows and borrows do not
after the frame    spawns, despawns, adds and removes, in order
```

```rust
enum Command {
    Spawn { signature: u64, entity: Option<Entity> },
    Despawn(Entity),
    Add { target: Target, id: u32, start: usize, len: usize },
    Remove { entity: Entity, id: u32 },
}
```

A Rust `enum` can carry different data in each variant, so each command holds
exactly what it needs. rin's `kayan_command` was one struct with every field,
and a `kind` saying which fields meant something. An add carries its value as
bytes: `len` bytes at `start` in the buffer's byte store.

```rust
struct Commands {
    list: Vec<Command>,
    bytes: Vec<u8>,
}
```

This is the **frame arena**, made of Vecs. After the commands are applied,
both are cleared. `clear` keeps the memory, so after a few frames the Vecs
are big enough for any frame, and recording a command allocates nothing.
rin's `memops_arena_clear` did the same thing for one block of memory.

## Step 3: recording

The typed methods a system calls copy the value's bytes into the store and
push a command:

```rust
    fn add<T: Component>(&mut self, target: impl Into<Target>, value: T) {
        let start = self.bytes.len();
        self.bytes.extend_from_slice(bytes_of(&value));
        self.list.push(Command::Add { target: target.into(), id: T::ID, start, len: size_of::<T>() });
    }
```

`bytes_of` is the course's fifth and last `unsafe` line: a `Pod` value as its
bytes, the opposite direction from 2.2's `slice`.

```rust
fn bytes_of<T: Pod>(value: &T) -> &[u8] {
    // SAFETY: T is Pod, so it has no padding and all its bytes are
    // initialised; the slice borrows `value` and cannot outlive it.
    unsafe { std::slice::from_raw_parts((value as *const T).cast::<u8>(), size_of::<T>()) }
}
```

rin's frame arena pushed each value at its type's alignment. Here the bytes
go into a `Vec<u8>` at whatever offset comes next, which is fine, because
they're only ever copied as bytes into a column, never read as a `T` where
they lie.

The fixed expire system is the broken loop with the despawn recorded:

```rust
fn expire_system<C>(it: &mut Iter, _ctx: &mut C) {
    let t = &it.tables[it.table];
    for (&e, l) in t.entities.iter().zip(t.slice::<Lifetime>()) {
        if l.seconds <= 0.0 {
            it.commands.despawn(e);
        }
    }
}
```

It's the version that didn't compile in Step 1, and now it does. `t` borrows
`it.tables`, and `it.commands` is a different field of the `Iter`, so the
loop can read the table and record at the same time. The table doesn't change
while the loop runs, so every row is looked at once.

```rust
struct Iter<'a> {
    tables: &'a mut [Table],
    table: usize,
    commands: &'a mut Commands,
    dt: f32,
}
```

3.2 noted that `Iter` has no world. That's what makes this the only way: a
system has the tables and the command buffer, and no method that changes
structure is in reach.

## Step 4: applying, by id

Commands hold bytes and ids, not types. So applying an add needs 2.6's add
*by id*:

```rust
    fn add_id(&mut self, e: Entity, id: u32, value: &[u8]) -> Result<(), Error> {
```

It's the same move-then-write as before, with the write a `copy_from_slice`
of the value's bytes into the row. Once that exists, the typed `add` from 2.6
shrinks to a one-line wrapper. That's the pattern from the start of the
course: byte work written once, a typed generic layer on top.

```rust
    fn add<T: Component>(&mut self, e: Entity, value: T) -> Result<(), Error> {
        self.add_id(e, T::ID, bytes_of(&value))
    }
```

`flush` applies the list in order, and `progress` calls it after the frame's
last system:

```rust
    fn flush(&mut self) {
        let mut cmds = std::mem::take(&mut self.commands);
        for i in 0..cmds.list.len() {
            let result = match cmds.list[i] {
                Command::Spawn { signature, .. } => {
                    let e = self.spawn(signature);
                    cmds.list[i] = Command::Spawn { signature, entity: Some(e) };
                    Ok(())
                }
                Command::Despawn(e) => self.despawn(e),
                Command::Add { target, id, start, len } => {
                    let e = cmds.resolve(target);
                    self.add_id(e, id, &cmds.bytes[start..start + len])
                }
                Command::Remove { entity, id } => self.remove_id(entity, id),
            };
```

The commands live in the world, and applying them calls `&mut self` methods
on the world. Reading `self.commands` while calling `self.spawn` would be two
overlapping borrows. `std::mem::take` moves the buffer *out* of the world,
leaving an empty one in its place, so the loop owns it outright. At the end,
it goes back, cleared, with its memory:

```rust
        cmds.list.clear();
        cmds.bytes.clear();
        self.commands = cmds;
```

Moving a `Commands` is copying two Vec headers, 48 bytes. The contents stay
where they are.

## Step 5: commands that arrive too late

By the time a command is applied, its entity may be gone. The usual case is
two systems both asking to despawn the same thing. Applying in order handles
that for free: the first despawn works, and the second finds a dead handle.
Part 1's generations make that check one comparison, and every method already
returns a `Result` that says so:

```rust
            match result {
                Ok(()) => self.applied += 1,
                Err(_) => self.skipped += 1,
            }
```

## Step 6: spawning from a system

A turret firing is a spawn in the middle of a frame. The new entity doesn't
exist until the commands are applied, so there's no handle to give its
components to. `commands.spawn` returns a **pending** spawn instead: the spawn
command's place in the list.

```rust
struct Pending(usize);
```

Components are given to that:

```rust
            let shot = it.commands.spawn(bullet_signature());
            it.commands.add(shot, *p);
            it.commands.add(shot, Velocity { per_second: Vec2 { x: 8.0, y: 0.0 } });
            it.commands.add(shot, Damage { amount: 25.0 });
            it.commands.add(shot, Lifetime { seconds: 2.0 });
```

`add` takes `target: impl Into<Target>`, "anything that converts into a
`Target`", and both `Entity` and `Pending` do:

```rust
enum Target {
    Entity(Entity),
    Pending(usize),
}
```

So `add(e, value)` and `add(shot, value)` are one method. rin needed two,
`kayan_defer_add` and `kayan_pending_set`.

When the flush reaches the spawn, it makes the entity and writes the handle
into the command (`entity: Some(e)` in Step 4). The adds after it look the
handle up there, through `resolve`. The bullet is spawned with its full
signature, so the adds land in the table it's already in: no moves. And it
doesn't move until the next frame, because no system ran over it this one.

## Step 7: a system with a context

A bullet that reaches a target damages it. The hit system walks the bullets
(its own query) and, for each, the targets (a second query). It needs that
second query from somewhere, so a system now gets a **context**, whatever
the game passes to `progress`:

```rust
type SystemFn<C> = fn(&mut Iter<'_>, &mut C);
```

`C` is a type parameter: the context is whatever type the schedule chooses.
This schedule's context is the targets query, so the hit system takes it
typed:

```rust
fn hit_system(it: &mut Iter, targets: &mut Query) {
```

rin's `ctx` was a `*void`, cast back to `*kayan_query` inside the system, and
nothing checked the cast. Here a system in a `System<Query>` schedule that
asked for some other context wouldn't compile. Systems that don't use the
context are generic over it (`expire_system<C>`), so they fit any schedule.
The program's second demo has no context to pass, so it passes `&mut ()`,
the empty type.

The hit system needs the bullets' table and a target's table at once, which
is 2.6's `get_disjoint_mut` again:

```rust
            let Ok([bullets, t]) = it.tables.get_disjoint_mut([it.table, ti as usize]) else {
                continue;
            };
```

`let ... else` is a pattern that must match, or the `else` runs (and must
leave the block: here, `continue`). If a table matched both queries, the two
indices would be the same, and the loop skips that pair instead of stopping.

The damage is a value, so it's written now. The bullet's despawn is
structure, so it's recorded. Walking a second query in the middle of a frame
is safe *because* of commands: no table is made or moved until the frame is
over, so the indices both queries hold stay good.

## Run it

```

    lifetimes:  0:1 0.00  1:1 1.00  2:1 0.00  3:1 0.00
    despawn 0:1
    despawn 2:1
    despawn 3:1
after one frame:
    lifetimes:  1:1 1.00
```

All three. Then the turret, with two targets 0.25 apart in its line of fire
and a third out of it:

```
3. a turret, two targets in its line of fire, one out of it
frame 1
    spawn {Position Velocity Damage Lifetime} -> 4:1
frame 2
frame 3
    spawn {Position Velocity Damage Lifetime} -> 5:1
frame 4
    despawn 4:1
    despawn 4:1: skipped, dead
frame 5
    spawn {Position Velocity Damage Lifetime} -> 4:2
...
health: 1:1 50, 2:1 50, 3:1 100

```

In frame 4, bullet `4:1` is close enough to both targets. Both lose 25, and
both hits record a despawn. The first applies; the second finds `4:1`
already dead and is skipped. In frame 5 the next bullet gets number 4 back
with generation 2: Part 1, working.

17 commands, for three bullets and two despawns: each spawn is five, the
spawn and its four components.

## Rust notes

| rin | Rust |
|---|---|
| a loop holding the table, calling `kayan_despawn`: compiles, misses rows | the same loop: E0502, doesn't compile |
| a loop over row numbers, calling `kayan_despawn` | the same: compiles, misses rows |
| `kayan_command { kind, entity, spawn, id, signature, value }` | `enum Command`: each variant carries only its own fields |
| `frame: memops_arena`, cleared after the flush | two Vecs, `clear`ed after the flush: same memory reused, no allocation |
| `kayan_defer_add` and `kayan_pending_set` | one `add(target: impl Into<Target>, value)` |
| `ctx: *void`, cast in the system | `C`, a type parameter: `hit_system(it, targets: &mut Query)` |
| `it*.world`, for `kayan_defer_*` | `it.commands`: the only structural change a system can reach |
| `memcpy` of `value&` into the arena | `bytes_of(&value)`, the fifth `unsafe` line, then `extend_from_slice` |
