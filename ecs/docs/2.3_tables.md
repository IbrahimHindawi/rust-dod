# 2.3 A table

`ecs/src/2.components/2.3.tables/tables.rs`

The two halves meet. Part 1 built the entity index: handles, slots, packed
rows, swap-remove. 2.1 and 2.2 built the component side: ids, a registry,
columns of bytes. A **table** is 1.4's packed rows with the typed Vecs
replaced by columns, one per component in its signature:

```
table {Position Velocity Health}
  entities  [ 0:1 | 3:1 | 2:1 | ... ]     who owns each row
  columns   Position [ ... ]  Velocity [ ... ]  Health [ ... ]
  capacity                                shared by every column
```

Row `r` is entity `entities[r]`, and its components are row `r` of every
column. This world still has a single table, so every entity has the same
components; 2.4 gives each combination its own.

## Step 1: the table

```rust
struct Table {
    signature: u64,
    capacity: usize,
    entities: Vec<Entity>,
    columns: [Option<Column>; 64],
}
```

- `signature` says which components the table has.
- `columns[id]` is `Some` when the signature has bit `id`, and `None`
  otherwise. 64 slots indexed by id means finding a column is an index, never
  a search. kayan in C looked columns up by name in a hash map, which is the
  thing this replaces.
- The row count is `entities.len()`, and `capacity` is the table's, shared by
  every column. Neither can disagree with the columns, because there's only
  one of each.

A table is made from a signature and the registry:

```rust
    fn new(infos: &[Option<&'static Info>; 64], signature: u64) -> Table {
        let mut columns = [const { None }; 64];
        for id in 0..64 {
            if signature & bit(id) != 0 {
                let info = infos[id as usize]
                    .unwrap_or_else(|| panic!("signature {signature} uses component {id}, which was never registered"));
                columns[id as usize] = Some(Column::new(id, info));
            }
        }
        Table { signature, capacity: 0, entities: Vec::new(), columns }
    }
```

The signature *is* the column list. In your C kayan, the signature and the
columns were written separately and could disagree (archetype `D` had
position columns its signature didn't mention). Here one is made from the
other.

`[const { None }; 64]` is how you fill an array with a value that isn't
`Copy`. A `Column` owns a Vec, so it can't be copied, and `[None; 64]` won't
compile; the `const` block makes 64 separate `None`s instead.

## Step 2: rows, for every column at once

Adding a row grows every column together when the table is full, then zeroes
the new row in each:

```rust
    fn add_row(&mut self, e: Entity) -> usize {
        if self.count() == self.capacity {
            self.grow();
        }
        let row = self.count();
        self.entities.push(e);
        for c in self.columns.iter_mut().flatten() {
            c.zero_row(row);
        }
        row
    }
```

`iter_mut().flatten()` walks the 64 slots and skips the `None`s, so the loop
body sees only the table's real columns, as `&mut Column`.

Removing a row is 1.4's swap-remove, for every column:

```rust
    fn remove_row(&mut self, row: usize, slots: &mut [Slot]) {
        let last = self.count() - 1;
        if row != last {
            for c in self.columns.iter_mut().flatten() {
                c.copy_row(row, last);
            }
        }
        self.entities.swap_remove(row);
        if let Some(moved) = self.entities.get(row) {
            slots[moved.index as usize].row = row as u32;
        }
    }
```

Compare it with 1.4's `despawn`: the same moves and the same slot fix, but
over columns of bytes instead of named Vecs. This function works for any table
that will ever exist.

Why does it take `slots` as an argument? The slots belong to the world, and
the table is a field of the world. In rin, `kayan_table_remove_row` took the
whole world and reached into both. In Rust, a method on the table borrows the
table, and nothing else; the world hands it the other thing it needs:

```rust
        self.table.remove_row(row, &mut self.slots);
```

`self.table` and `self.slots` are two fields, so the compiler lets them be
borrowed at the same time, one by the method and one as its argument. Taking
`&mut World` instead would borrow the table twice, and wouldn't compile.
Passing what a function needs, rather than the world, is a habit you'll see
for the rest of the course.

## Step 3: the typed view of a table

```rust
    fn slice<T: Component>(&self) -> &[T] {
        self.column::<T>().slice::<T>(self.count())
    }
```

`t.slice::<Position>()` is the table's position column as a `&[Position]`, cut
to the rows in use. Systems will live on this in Part 3: get the slices, loop
over rows. A table without the column stops the program with a message saying
which one:

```rust
    fn column<T: Component>(&self) -> &Column {
        self.columns[T::ID as usize]
            .as_ref()
            .unwrap_or_else(|| panic!("the table has no {} column", T::INFO.name))
    }
```

## Step 4: the world

```rust
struct World {
    infos: [Option<&'static Info>; 64],
    component_count: u32,
    slots: Vec<Slot>,
    free: Vec<u32>,
    live: usize,
    table: Table,
}
```

The registry from 2.1, the slots and free list from Part 1, and one table.
Spawning is Part 1's spawn with the row coming from the table:

```rust
        let e = Entity { index, generation: self.slots[index as usize].generation };
        self.slots[index as usize].row = self.table.add_row(e) as u32;
        self.live += 1;
        e
```

and despawning is Part 1's despawn calling `remove_row`.

## Step 5: writing a new entity's data

There's no typed `get` or `set` yet (that's 2.5), so the program finds the
row and writes through the column slices:

```rust
        let row = w.row(e);
        w.table.slice_mut::<Position>()[row] = Position { at: Vec2 { x: 10.0 * i as f32, y: 0.0 } };
        w.table.slice_mut::<Velocity>()[row] = Velocity { per_second: Vec2 { x: 0.0, y: 1.0 } };
        w.table.slice_mut::<Health>()[row] = Health { points: 100.0, max: 100.0 };
```

Each line borrows the table, writes one row, and lets go, so the next line can
borrow it again. Keeping all three slices at once would need three `&mut`
borrows of one table, which the compiler refuses. 2.5 comes back to that.

Reading two columns at once is fine, since both are shared borrows. The
printer zips them with the entities and walks all three together:

```rust
    for (row, ((e, p), h)) in t.entities.iter().zip(t.slice::<Position>()).zip(t.slice::<Health>()).enumerate() {
```

## Run it

```
spawned 6 drones into one table; it grew from 4 rows to 8
    6 rows, room for 8
    row 0  0:1  position ( 0.00,  0.00)  health 100
...
despawn 0:1 and 3:1
    4 rows, room for 8
    row 0  5:1  position (50.00,  0.00)  health 100
    row 1  1:1  position (10.00,  0.00)  health 100
    row 2  2:1  position (20.00,  0.00)  health 100
    row 3  4:1  position (40.00,  0.00)  health 100
spawn 3:2: a reused number, the next row, zeroed except what we set
...
verify: 0 problems
```

Row 0 went to `5:1` (the last row moved into the hole), then row 3 went to
`4:1` the same way. Every column moved together, and the slots followed.

## Rust notes

| rin | Rust |
|---|---|
| `columns: [64]kayan_column`, unused ones zeroed | `[Option<Column>; 64]`: unused ones are `None`, and you can't use one by accident |
| `if (kayan_table_has(t, id))` around each column | `self.columns.iter_mut().flatten()`: only the `Some`s |
| `count` kept next to `entities` | `entities.len()`: one number, never out of step |
| `remove_row(w: *kayan_world, t: *kayan_table, ...)` | `table.remove_row(row, &mut self.slots)`: borrow only what's needed |
| `printfmt(...); exit(1);` | `panic!(...)`, or `unwrap_or_else(\|\| panic!(...))` on an `Option` |
| a `[64]` of structs, zeroed with `= {}` | `[const { None }; 64]`, for a type that isn't `Copy` |
