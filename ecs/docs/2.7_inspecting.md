# 2.7 Inspecting the world

`ecs/src/2.components/2.7.inspecting/inspecting.rs`

**In the dojo:** [11. a reflection walk](../../dojo/11.reflect/README.md), on its own, to watch and to practise.

The world can store, copy and move any component, but it can't show you one.
When something goes wrong at frame 3,000, you want to see an entity: every
component it has, every field, with names. In C that means writing a printer
per component and keeping each in step with its struct. rin's compiler writes
a **reflect record** for every struct: its fields, with their names, types and
byte offsets. Rust has no such records built in, but the macro that already
declares each component can write one. The world registered the records back
in 2.1 to learn component sizes. Here they pay off a second time.

```
w.inspect(e)          every component of e, field by field
w.print_layout()      every table, its columns, and their memory
```

Neither names a single component type. Add a component tomorrow and both
print it.

## Step 1: records with fields

2.1's record had a name and a layout. Now it lists the fields too:

```rust
struct Info {
    name: &'static str,
    layout: Layout,
    fields: &'static [Field],
}

struct Field {
    name: &'static str,
    offset: usize,
    size: usize,
    ty: &'static str,
    info: Option<&'static Info>,
    hidden: bool,
}
```

A field's record says where its bytes are in the struct (`offset`, `size`),
and what they are. `info` is the field type's own record when it's a struct
(`at: Vec2` inside `Position`), and `None` when it's a builtin like `f32`,
which tools read by its type's name, `ty`.

## Step 2: the compiler fills them in

`pod!` writes the record, one `Field` per field it declares:

```rust
        impl Reflect for $name {
            const RECORD: Option<&'static Info> = Some(&Info {
                name: stringify!($name),
                layout: Layout::new::<$name>(),
                fields: &[$(Field {
                    name: stringify!($field),
                    offset: std::mem::offset_of!($name, $field),
                    size: size_of::<$ty>(),
                    ty: stringify!($ty),
                    info: <$ty as Reflect>::RECORD,
                    hidden: is_hidden!($($attr)?),
                }),*],
            });
        }
```

`$( ... ),*` repeats once per field. Every value in it comes from the
compiler: `offset_of!` is the field's byte offset, as the compiler laid it
out, so the record can't disagree with the struct.

`<$ty as Reflect>::RECORD` is the field type's record, and that's how nesting
works. Every type a component is made of implements `Reflect`. Structs made
with `pod!` have a record; builtins say they don't:

```rust
trait Reflect {
    const RECORD: Option<&'static Info>;
}

impl Reflect for f32 {
    const RECORD: Option<&'static Info> = None;
}
```

The whole record, nested records included, is a constant built at compile
time. Nothing is computed when the program starts.

## Step 3: a component as bytes

Tools work from records, not types, so they need the byte view:

```rust
    fn get_bytes(&self, e: Entity, id: u32) -> Option<&[u8]> {
        if !self.alive(e) || id >= self.component_count {
            return None;
        }
        let row = self.row(e);
        self.table_of(e).columns[id as usize].as_ref().map(|c| c.row(row))
    }
```

It's `get::<T>`'s path, stopping one step early: the row's bytes as a slice,
sized by the column. `.map(|c| c.row(row))` turns the `Option<&Column>` into
an `Option<&[u8]>`: `None` stays `None`, and a column becomes its row. Game
code uses the typed layer; tools use this.

## Step 4: walking fields

```rust
fn print_fields(info: &Info, base: &[u8], depth: usize) {
    for f in info.fields.iter().filter(|f| !f.hidden) {
        let at = &base[f.offset..f.offset + f.size];
        print!("{:indent$}{}:", "", f.name, indent = depth * 4);
        match f.info {
            Some(inner) => {
                println!();
                print_fields(inner, at, depth + 1);
            }
            None => {
                print!(" ");
                print_builtin(f.ty, at);
                println!();
            }
        }
    }
}
```

For each field the record lists, cut its bytes out of the component by offset
and size. A struct field has a record of its own, so the printer recurses into
it. A builtin is printed by its type's name:

```rust
        "f32" => print!("{:.2}", f32::from_ne_bytes(at.try_into().expect("4 bytes"))),
```

`at.try_into()` turns the `&[u8]` slice into a `[u8; 4]` array, failing if
it isn't 4 bytes long, and `f32::from_ne_bytes` turns 4 bytes into a float.
No pointer cast, so no `unsafe`: the inspector reads any component through
safe code.

Because each field's bytes are cut with a bounds-checked slice, a record that
disagreed with the data would stop the program instead of printing garbage.

## Step 5: hiding bookkeeping

A field can be marked `#[hidden]`:

```rust
component!(Turret { cooldown: f32, #[hidden] timer: f32 });
```

That looks like a Rust attribute, but it's only text the macro matches. The
pattern `$(#[$attr:ident])?` takes an optional `#[word]` before a field, and
`is_hidden!` turns it into the record's `hidden` flag:

```rust
macro_rules! is_hidden {
    () => {
        false
    };
    (hidden) => {
        true
    };
}
```

No attribute gives `false`; `#[hidden]` gives `true`; any other word is a
compile error, because no rule matches it. The inspector skips hidden fields.
The component decides what a tool shows; the tool doesn't need to know the
component.

## Step 6: an entity, and the layout

`inspect` walks the entity's signature and prints each component with
`print_fields`:

```rust
        for id in (0..self.component_count).filter(|&id| signature & bit(id) != 0) {
            let info = self.info(id);
            println!("    {}", info.name);
            print_fields(info, self.get_bytes(e, id).expect("e has it"), 2);
        }
```

`print_layout` walks every table and prints each column's row size and bytes
used out of bytes allocated, which shows where memory goes.

## Run it

```
0:1 {Position Turret}
    Position
        at:
            x: 0.00
            y: 0.00
    Turret
        cooldown: 0.50
...
2:1 {Position Velocity Health Burning}
...
    Health
        points: 60.00
        max: 100.00
    Burning
        per_second: 10.00
...
1:1 (dead)
```

```
table 1 {Position Velocity Health}: 0 rows, room for 4
    Position   8 bytes a row,    0 of   32 bytes in use
    Velocity   8 bytes a row,    0 of   32 bytes in use
    Health     8 bytes a row,    0 of   32 bytes in use
```

The turret's `timer` isn't printed. Table 1 is empty but keeps its capacity:
drone `1:1` was its only remaining row after `2:1` caught fire and moved out,
and then `1:1` was despawned. Tables never shrink in this course. A real
engine might trim empty ones between levels.

## Part 2 in one picture

```
handle 2:1 ──> slots[2] { generation 1, table 2, row 0 }
                                         │
table 2 {Position Velocity Health Burning}
  entities  [ 2:1 ]
  Position  [ (30, -5) ]     Velocity [ (-1, 0) ]     Health [ 60/100 ]     Burning [ 10 ]
  add_edges / remove_edges ──> neighbouring tables in the archetype graph
```

The storage half of the ECS is done: identity (Part 1), and any component, in
any combination, changing at run time (Part 2). Part 3 is the behaviour:
queries to find tables, and systems to run over them.

## Rust notes

| rin | Rust |
|---|---|
| `position<>`, a record the compiler writes for every struct | a record `pod!` writes, from `stringify!`, `offset_of!` and `size_of` |
| `f*.info`, the field type's record, or `null` | `<$ty as Reflect>::RECORD`: `Some` for a `pod!` struct, `None` for a builtin |
| `timer: f32 @ "hidden"` | `#[hidden] timer: f32`, matched by the macro, not a real attribute |
| `reflect_field_has_attr(f, "hidden")` | `f.hidden`, a `bool` the macro set |
| `cast(at.data, *f32)*` | `f32::from_ne_bytes(at.try_into()...)`: bytes to a number, no `unsafe` |
| `printf("%*s", depth * 4, "")` | `print!("{:indent$}", "", indent = depth * 4)` |

Rust crates like `bevy_reflect` do this with *derive macros*, which can read a
whole struct definition and write any code about it. `macro_rules!` is
simpler and in the language itself, at the cost of declaring components in the
macro's own syntax.
