# 2.4 Many tables: archetypes

`ecs/src/2.components/2.4.archetypes/archetypes.rs`

**In the dojo:** [3. the slot map](../../dojo/3.slot_map/README.md), on its own, to watch and to practise.

2.3's world had one table, so every entity had the same components. Real
games mix: a turret has a position and a turret component, a drone has a
position, velocity and health, a bullet has a position, velocity, damage and
lifetime. Each combination gets **a table of its own**. Every row of a table
has every component in its signature, so there are no holes and no flags.
A table for one combination is called an **archetype**.

```
table 0 {Position Turret}                   0:1
table 1 {Position Velocity Health}          1:1 2:1 3:1
table 2 {Position Velocity Damage Lifetime} 4:1 5:1
```

Nobody declares the archetypes. The first time something spawns with a new
combination, the world makes its table and remembers it by signature, so the
next spawn finds it.

## Step 1: slots say which table

```rust
struct Slot {
    generation: NonZeroU32,
    table: u32,
    row: u32,
}
```

Handle to slot to **(table, row)**. That's the whole entity index from here
on.

## Step 2: the world keeps every table

```rust
struct World {
    infos: [Option<&'static Info>; 64],
    component_count: u32,
    tables: Vec<Table>,
    by_signature: HashMap<u64, u32>,
    slots: Vec<Slot>,
    free: Vec<u32>,
    live: usize,
}
```

`tables` holds them all, and `by_signature` maps a signature to its table's
index. **Tables are referred to by index, never by reference.** Making a new
table can grow the `tables` Vec and move every table in memory, and an index
survives that. A reference is good until the next table is made, and Step 4
shows the compiler holding you to it.

## Step 3: where archetypes come from

```rust
    fn table_for(&mut self, signature: u64) -> u32 {
        if let Some(&index) = self.by_signature.get(&signature) {
            return index;
        }
        let index = self.tables.len() as u32;
        self.tables.push(Table::new(&self.infos, signature));
        self.by_signature.insert(signature, index);
        index
    }
```

Found, or made. A game has tens of archetypes, maybe a few hundred, so a
linear search would do too. `HashMap` is in the standard library, so the map
costs nothing to add, and 2.6 makes the lookup rare anyway.

`if let Some(&index) = ...` is a pattern: `get` returns `Option<&u32>`, and
`Some(&index)` matches the `Some` and copies the number out of the reference
in one go.

## Step 4: spawning takes a signature

```rust
    fn spawn(&mut self, signature: u64) -> Entity {
```

and puts the new entity in that signature's table:

```rust
        let table = self.table_for(signature);
        let row = self.tables[table as usize].add_row(e);
        self.slots[index as usize] = Slot { generation: e.generation, table, row: row as u32 };
```

The order matters: the table is reached **after** `table_for`, because
finding the table can make one and move the rest. In rin, getting this order
wrong is the classic archetype-ECS bug. It works until the first new
archetype appears mid-game, and then a row goes into a table that no longer
exists.

In Rust, the wrong order doesn't compile. Take the reference first:

```rust ignore
        let t = &mut self.tables[0];
        let table = self.table_for(signature);
        let row = t.add_row(e);
```

```
error[E0499]: cannot borrow `*self` as mutable more than once at a time
    |
391 |         let t = &mut self.tables[0];
    |                      ----------- first mutable borrow occurs here
392 |         let table = self.table_for(signature);
    |                     ^^^^ second mutable borrow occurs here
393 |         let row = t.add_row(e);
    |                   - first borrow later used here
```

`t` borrows the world's tables, and `table_for` needs the whole world
mutably, so the two can't overlap. The compiler doesn't know that
`table_for` might move the tables; it only knows that it *could* change
anything in the world, and that's enough to rule the bug out. This is the
same rule that kept 2.2's references out of a growing column, applied one
level up.

Despawning finds the table through the slot:

```rust
        let Slot { table, row, .. } = self.slots[e.index as usize];
        self.tables[table as usize].remove_row(row as usize, &mut self.slots);
```

`let Slot { table, row, .. } = ...` copies two fields out of the slot by
name, and `..` skips the rest. Then the call borrows one table and the slots,
which are two different fields of the world, as in 2.3.

## Step 5: the invariant, over every table

`verify` now walks every table: each row belongs to a live entity whose slot

## Step 6: one column, many tables

The end of the program reads every position in the world:

```rust
    for (ti, t) in w.tables.iter().enumerate() {
        for (row, (e, p)) in t.entities.iter().zip(t.slice::<Position>()).enumerate() {
```

The position column of each table, in turn. Positions are no longer one
array; they're one array per archetype that has them. This is exactly what a
query does in Part 3: visit the tables that have the right components, and
stream their columns.

## Rust notes

| rin | Rust |
|---|---|
| `hashmap<u64, u32>` from rin's std | `std::collections::HashMap<u64, u32>` |
| `found: *u32 = get(...); if (found != null)` | `if let Some(&index) = self.by_signature.get(&signature)` |
| `kayan_table_at(w, index)`, a pointer good until the next table | `&mut self.tables[index]`, a borrow the compiler won't let outlive a change to the world |
| taking the table pointer before `kayan_table_for`: a quiet bug | the same order is a compile error (E0499) |
| `slot*.table`, `slot*.row` | `let Slot { table, row, .. } = ...`: copy fields out by name |

The borrow checker caught this bug because it's about **references**: a
`&mut Table` that would have outlived its table. It still can't catch 1.2's
bug, a stale **number**. An old table *index* stays a valid number after
anything, as long as no tables are ever removed, which in this course they
never are.
